# Bonus and stand-out items

Everything below was verified on the local k3d cluster (k3s v1.35), not just written.

| Item | Status | Evidence / where |
|---|---|---|
| **Bonus: multi-store provisioning** | Done | Stores page and `gateway/stores.py` (API). `gateway/provisioner.py` reconciles from Postgres in a separate Deployment. Each store gets its own namespace, random Secrets, the same `charts/store` via helm with ResourceQuota + LimitRange, its own DB/PVCs/Ingress host, and an MCP server auto-registered as `shop-<slug>` (marked Ready only once the gateway lists its tools). Live: two stores provisioned in parallel (~100 s); the chat agent compared today's orders across Berlin and Paris via `shop-berlin__list_orders` / `shop-paris__list_orders`; deleting Berlin removed its tools, release, namespace, both PVs and Secrets in 27 s; killing the provisioner 22 s into `helm install` → the new pod uninstalled the `pending-install` release and finished the store. Isolation: berlin's woo-mcp cannot reach paris's WordPress, MariaDB or woo-mcp (NetworkPolicies). Guardrails: per-namespace quota/limits, 2 stores per user, 15 min deadline, idempotent create, retry of failed stores. Tests: `tests/test_provisioner.py`, `test_store_api_is_idempotent_limited_and_scoped`. |
| **1. Production-like deployment** | Rehearsed on a second k3s cluster, not on a real VPS | `scripts/prod-rehearsal.sh` runs both charts with `values-prod.yaml` on cluster `woo-prod`. Only DNS names, the registry and the CA issuer differ (`deploy/rehearsal/`). Results: cert-manager issued `platform-tls` and `storefront-tls`; all five images were pulled from the registry at `1.0.0`; `PUBLIC_URL=https://…` with `COOKIE_SECURE=true`; the full smoke test passed **18/18 over HTTPS** (chat included), verified against the CA; a store provisioned there came up as `https://lyon.127-0-0-1.sslip.io` with its own `store-lyon-tls` certificate and quota. A real VPS needs an account; the README has the exact steps (same commands, Let's Encrypt issuer in `deploy/cluster-issuer.yaml`). |
| **2. Tool permissions** | Done (per role and per user) | Per-tool *admins only* flags in the dashboard; restricted tools are hidden from `tools/list` (MCP, chat, dashboard, discover search) and rejected if called (`denied` in the audit log). Per-user: a server's owner (e.g. the member who provisioned a store) may use that server's admin-only tools. `mcp_endpoint.Gateway.allowed`. |
| **3. OAuth on the gateway** | Done | `gateway/oauth.py`: RFC 9728 protected-resource metadata and the 401 `resource_metadata` challenge, RFC 8414 + OIDC discovery, Client ID Metadata Documents and RFC 7591 registration, PKCE S256, RFC 8707 resource binding (tokens only valid for this gateway's `/mcp`), RFC 9207 `iss`, rotating refresh tokens with replay → grant revoked, dashboard consent page and *Connected apps* with disconnect. Live through the Ingress: discovery → registration → consent → token → 25 tools, calls audited as `oauth:<client>`, disconnect → 401. Test: `test_oauth_browser_login_flow`. |
| **4. Handling many tools** | Done | `/mcp?tools=discover` exposes `gateway__list_servers`, `gateway__search_tools`, `gateway__call_tool` (same permissions and audit); live search for "orders today paris" ranks `shop-paris__list_orders` first. The chat agent switches to the same search/call pattern above 40 tools. |
| **5. Hosted MCP servers** | Done | *Deploy from image*: namespace `mcp-<slug>` with a Secret for env (encrypted in the gateway), non-root read-only container, limits, quota, NetworkPolicy (only the gateway in; egress only DNS unless allowed). Live: `utils-mcp:dev` deployed as `calc` and connected in 15 s; a bad image failed in 6 s with the pull error as the reason; both removed cleanly in 33 s. |
| **6. Security hardening** | Done | SSRF guard (save time and every connection; loopback, link-local, metadata, private/cluster ranges unless allow-listed). Credentials encrypted at rest (Fernet). Default-deny NetworkPolicies everywhere. Every container non-root, including WordPress (uid 33 on :8080). No service-account tokens except the provisioner's. **Least-privilege RBAC**: the provisioner can only create/delete namespaces and bind one ClusterRole; its rights inside a namespace come from a RoleBinding it creates there; a ValidatingAdmissionPolicy limits it to `store-*`/`mcp-*` namespaces carrying its own `managed-by` label. Live: it cannot read `platform` or `store-main` Secrets, delete `store-main`/`kube-system`, create other namespaces, or bind roles outside its namespaces (a hole that let it delete `store-main` was found this way and closed). |
| **7. Scaling** | Done | Two gateway replicas with stateless Streamable HTTP; live, 12 MCP requests split 6/6 across the pods (`X-Served-By` header). Shared state in Postgres. Per-user rate limit consistent across replicas. Two dashboard replicas. |
| **8. Observability** | Done | `/metrics` (cluster-internal): tool calls by server, source and outcome, latency histograms, upstream up/down, probe latency, auth failures, chat outcomes. Dashboard: per-server 24 h calls, error rate, average latency; a plain-language reason for every unreachable upstream, failed call, failed store or failed hosted deploy. |
| **9. Upgrades and rollback** | Done, measured | `scripts/upgrade-rollback-demo.sh`: upgrade all images to a new tag, `helm rollback`, and a broken `--atomic` upgrade that Helm reverts itself. 0 of 402 probe requests failed (`preStop` drain + `maxUnavailable: 0`; 5/417 failed before the drain was added). Database changes are additive only (nullable columns added at startup), so an older gateway runs against a newer schema. |
