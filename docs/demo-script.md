# Demo video script (about 20 minutes)

The order follows the six parts the brief asks for, then the bonus. Commands run
in WSL Ubuntu from the repo root. Keep that terminal open: WSL stops the cluster
when no session is attached.

**Before recording**
- `scripts/local-up.sh` (or `k3d cluster start woo`), then `scripts/smoke-test.sh` once so everything is warm.
- Print the logins: `kubectl -n platform get secret platform-secrets -o jsonpath='{.data.admin-password}' | base64 -d`.
- Browser windows:
  - **A**: normal window, http://app.localtest.me, signed in as admin (user A).
  - **B**: private window, used for user B.
  - **Shop**: http://shop.localtest.me.
- Have a terminal ready for Claude Code or MCP Inspector (user B's client).

---

## 1. System design and the definition-of-done flow (6 min)

**Architecture (1 min).** Show the README diagram. Name the components:
- the store (WordPress, WooCommerce, MariaDB);
- woo-mcp, the store's MCP server, written from scratch;
- the gateway: dashboard API, the `/mcp` aggregator and the chat agent;
- the dashboard;
- two more upstreams, shipping and utilities;
- the provisioner.

Point out that nothing talks to an upstream except the gateway.

**Store.**
1. In **Shop**, add *Classic Tee* to the cart and check out with **Cash on delivery**.
2. In http://shop.localtest.me/wp-admin → WooCommerce → Orders, the order is *Processing*.

**Team.**
1. In **A**, go to **Members → Invite** `bob@example.com` (member) and copy the link.
2. In **B**, open the link, set a password, then go to **API keys → Generate key**.

**Chat as user A.**
1. On **Chat**, ask *"Create a product called Demo Mug priced at 14.50"*. Expand the tool call card (`woocommerce__create_product`).
2. Refresh **Shop**: Demo Mug is there. Buy one with COD.
3. Ask *"What orders came in today?"*. The agent calls `woocommerce__list_orders {period: today}` and lists the order.

**External client as user B.**
- Claude Code:
  ```
  claude mcp add --transport http team-gateway http://app.localtest.me/mcp --header "Authorization: Bearer <B's key>"
  ```
- Or MCP Inspector: Streamable HTTP, the same URL, the key as the Bearer token.

Then:
1. List tools: `woocommerce__*`, `shipping__*`, `utilities__*`. B doesn't see `woocommerce__create_product` (admin-only).
2. Ask *"What orders came in today?"*.
3. Ask a prompt that needs two servers: *"What did today's orders add up to in EUR?"* (`woocommerce__list_orders` + `utilities__convert_currency`).

**Team and control.**
1. **Revoke** B's key (in **B**: API keys → Revoke). B's next call gets 401.
2. In **A**: **Servers → Shipping → Disable**. Shipping's tools disappear from the chat (new question) and from B's client (re-list).
3. Kill an upstream:
   ```
   kubectl -n platform delete pod -l app.kubernetes.io/name=utils-mcp
   ```
   Or, so it stays down long enough to show, scale it to 0:
   ```
   kubectl -n platform scale deploy/utils-mcp --replicas=0
   ```
   **Servers** shows Utilities as *Unreachable* with its reason, and WooCommerce calls still work. Scale back to 1.
4. **Audit log**: every call above is listed with user, source (`mcp` / `chat` / `oauth`), server, tool, duration and outcome, including `denied`, `rejected` (revoked key) and `unreachable`.

## 2. Kubernetes (3 min)

```
kubectl get ns
kubectl -n platform get deploy,sts,svc,ingress,pvc,secret
kubectl -n store-main get deploy,sts,svc,ingress,pvc,secret
kubectl -n platform get deploy gateway -o jsonpath='{.spec.template.spec.containers[0].resources}{"\n"}{.spec.template.spec.containers[0].readinessProbe}{"\n"}'
kubectl get networkpolicy -A
```

- **Public:** only what the two Ingresses route: the storefront host, and `app.` for `/`, `/api`, `/mcp`, `/oauth` and `/.well-known`.
- **Internal only:** woo-mcp has no Ingress, a ClusterIP Service, and a NetworkPolicy that admits only gateway pods. Demonstrate:
  ```
  kubectl -n platform exec deploy/utils-mcp -- python -c "import urllib.request; urllib.request.urlopen('http://woo-mcp.store-main.svc.cluster.local:8000/healthz', timeout=5)"
  ```
  It times out. The same command from `deploy/gateway` works.
- **Secrets:** generated by `scripts/secrets.sh` into Kubernetes Secrets. No secret is in git or in values files.
- **Volumes:** MariaDB, the WordPress content and Postgres are on PVCs (`local-path`).

## 3. MCP internals (3 min)

**A call's path.** Walk through the diagram in `docs/design.md`:
1. client → Traefik → a gateway replica;
2. API key HMAC lookup;
3. `woocommerce__list_orders` resolved to the woocommerce upstream;
4. permission, rate limit and SSRF re-check;
5. a fresh Streamable HTTP session with the server-side bearer token;
6. woo-mcp signs OAuth 1.0a → WooCommerce REST → MariaDB;
7. the result comes back and an audit row is written.

**Name collisions.** Show `woocommerce__get_order` next to `shipping__get_order`. Every tool is always prefixed, so names stay stable when servers are added.

**Timeouts and dead upstreams.**
- Each call has a per-server deadline.
- `tools/list` reads a cache that a 10-second health loop maintains, so it never waits on a dead server.
- A dead upstream's tools leave the list. A call to it returns *"Upstream 'Utilities' failed: connection refused or no route to host. Other servers are unaffected."*

**Two replicas.** `curl -sI http://app.localtest.me/healthz | grep -i served` a few times: the `x-served-by` value alternates between the two gateway pods.

## 4. Security posture (3 min)

**Keys and credentials.**
- API keys are 256-bit random, shown once and stored as HMAC-SHA256 with a pepper.
- Upstream credentials are Fernet-encrypted at rest, never returned by the API (the dashboard shows "credential stored encrypted"), and never sent to a client.

**What a member can and can't do.**
- Members can use tools that aren't admin-only, and see only their own keys and audit rows.
- They can't manage servers or members, and can't see upstream URLs or credentials.
- Show B's denied `update_order_status` in the audit log.

**A malicious upstream.** See `docs/threat-model.md`:
- its tools are forced under its own prefix, so it can't shadow `woocommerce__…`;
- descriptions are capped, and the agent's instructions treat tool output as data;
- write tools are admin-only, so they aren't in a member's tool list;
- the SSRF guard stops admin URLs pointing at cluster or metadata addresses (try adding `http://169.254.169.254/` → refused);
- the server only ever sees its own credential.

**Least privilege.** Only the provisioner can call the Kubernetes API, and only inside the namespaces it created:
```
kubectl auth can-i get secrets -n platform --as=system:serviceaccount:platform:store-provisioner     # no
kubectl delete ns store-main --as=system:serviceaccount:platform:store-provisioner --dry-run=server  # denied by policy
```

## 5. Chat agent (1.5 min)

- In `gateway/chat.py`, the agent is an MCP client of the gateway's own `/mcp`, using a five-minute token bound to the signed-in user. So the tool list, permissions and audit rows are that user's, with source `chat`.
- The loop: model → tool calls → MCP `call_tool` → results back to the model, at most 8 steps.
- Ask a multi-step question and expand each tool card.

## 6. Local to production (2.5 min)

**What changes is values only.** Show this side by side:
```
diff <(helm template p charts/platform -f charts/platform/values-local.yaml) <(helm template p charts/platform -f charts/platform/values-prod.yaml) | head -40
```
- Domains: `localtest.me` → a real domain or `sslip.io`.
- TLS: cert-manager with `letsencrypt-prod`, and Secure cookies.
- Images: imported locally → pulled from GHCR.
- Storage class and sizes.
- Secrets: the same Secret names, from the script or a secret manager.

**Rehearsal.** `scripts/prod-rehearsal.sh` runs exactly `values-prod.yaml` with HTTPS on a second k3s cluster. Show https://app.127-0-0-1.sslip.io with its certificate issued by cert-manager.

**Upgrade and rollback.** Run `scripts/upgrade-rollback-demo.sh`: upgrade to `1.0.1`, `helm rollback`, then a broken `--atomic` upgrade that Helm reverts. It ends with *"0 failed"* requests.

## Bonus: multi-store (2 min)

1. In **A**, go to **Stores** and create `berlin` and `paris`. Both show *Provisioning* with their current step, then *Ready* with links. Show `kubectl get ns` and `kubectl -n store-paris get resourcequota`.
2. Buy something in each storefront.
3. On **Chat**, ask *"Compare today's orders across the Berlin and Paris stores"*. It calls `shop-berlin__list_orders` and `shop-paris__list_orders`.
4. **Delete** Berlin. Its `shop-berlin__*` tools leave the gateway at once. Then `kubectl get ns,pv` shows `store-berlin` and its volumes gone.
5. Optional: kill the provisioner pod while a store is installing. It still finishes, and the log shows *"stuck in pending-install; uninstalling before retry"*.
